# Frontend

Svelte 5 (runes) + Vite + TypeScript strict, served by the FastAPI backend
(ADR-0002). Views: "Now", the setup wizard (`#/setup/<step>`) and the settings overview (`#/settings`).

```bash
cd frontend
npm ci
npm run dev            # Vite on :5173, proxies /api and /health to 127.0.0.1:8099
npm run gen:api        # regenerate src/lib/api/schema.d.ts from openapi.json
npm run verify         # gen:api check, lint, format, svelte-check, vitest, build, size
npm run test:e2e       # Playwright against the demo backend (builds the SPA first)
```

Demo backend: `SUNCORE_DEMO=1 SUNCORE_STATIC_DIR=frontend/dist uv run python -m suncore`.
`openapi.json` is generated by `scripts/export_openapi.py`; never edit it by hand.
`schema.d.ts` is generated and carries no SPDX header.

## Rules

- All URLs are resolved against the current document (`new URL('api/v1/...', location.href)`),
  never `/api/...`: the ingress base path is dynamic. Vite `base: './'`, hash routing.
- No UI text in markup outside `t()` (`eslint/no-hardcoded-text.js`, tested). Keys live in
  `src/lib/i18n/locales/en.json` (source) and `de.json`; `scripts/check_reasons.py` verifies
  that backend `Reason` keys and `api.error.*` details exist in both.
- One WebSocket (`src/lib/stores/live.svelte.ts`) feeds all views; reconnect with jittered
  exponential back-off (`src/lib/api/ws.ts`). Flow lines use CSS animations on quantised speed
  levels, so a new value never restarts an animation unless the power class changes.
- Bundle budget (`npm run size`): everything except ECharts < 250 kB gzip, first paint < 125 kB,
  the on-demand ECharts chunk (plan view only, never in the first paint) < 200 kB.
- `.npmrc` sets `legacy-peer-deps=true`: npm 10.9 crashes (`edgesOut` of null in arborist) when
  resolving vitest's optional peer set. All peers we need are listed explicitly in `package.json`.

## Plan view and battery card (Phase 4)

`#/plan` loads `PlanChart.svelte` (the only importer of ECharts) on demand. The option is a pure
function (`plan/chartOption.ts`), the data series, the next-actions list and the preview numbers
come from `plan/model.ts`. "Now" is the plan's hand-over time. The Now view shows the battery
card and the next planned actions; the wizard steps 4, 5, 6, 8 and 10 carry the Phase 4 forms
(`wizard/batteryForm.ts`, `tariffForm.ts`, `scheduleForm.ts`, `forecastForm.ts`). The demo battery
adapter for Playwright and screenshots is switched on with `SUNCORE_DEMO_BATTERY_CONTROL=1`.

## Setup wizard (Phase 2)

- Routes: `#/setup` resumes at the first step not in `wizard.completed_steps`; `#/setup/<step>`
  opens one step (`region`, `energy`, `grid`, `pv`, `battery`, `tariff`, `devices`, `priorities`,
  `mode`, `summary`; ids in `src/lib/wizard/steps.ts`). Without a completed wizard the first visit
  of `#/` is redirected once to the wizard; leaving it is allowed.
- `#/settings` is an overview of all sections with "Edit" links into single steps, the restore of
  earlier versions (`/config/{section}/history`) and export/import.
- Logic lives in plain modules (`src/lib/wizard/*.ts`: form <-> section mapping, priority reducer,
  suggestions) with Vitest tests; `stores/wizard.svelte.ts` holds the forms and saves a section per
  step with `PUT`. 422 issues (`{loc, key, args}`) are rendered through the `api.validation.*`
  catalogue keys next to the field (`wizard/issues.ts`) and as a list in the shell.
- Components: `WizardShell` (progress, back/skip/next, focus on the step heading), `RolePicker`
  (combobox over `/entities?role=` or `?template=&role=&device_id=`, shows ranking criteria),
  `SignCheck` (live plausibility question through `POST /preview` with one-click inversion),
  `UnitBadge`, `NumberField`, `TemplateGallery`, `DeviceEditor`. Steps are lazy-loaded chunks.
- The tariff section needs import and export prices. The forecast source chosen in the Solar step
  is its own section (`forecast`) and is stored right there, no tariff needed.
- Unsaved edits: `wizard.dirty()` compares every form with the stored section. Leaving the wizard
  asks first, Settings never reloads over unsaved edits (it offers to discard them), and
  `beforeunload` asks on tab close.
- The operating-mode step stores all three modes; only shadow is active (the gate ignores the
  section until Phase 3).

## Theme bridge (BRIEF R6)

`src/lib/theme/bridge.ts` runs at start (`main.ts`). Under ingress the panel is an iframe of the HA
frontend. If `window.parent.document` is readable (same origin), the HA theme variables listed in
`THEME_MAP` (`--primary-color`, `--primary-text-color`, `--card-background-color`, ...) are copied
from the parent's root onto our `:root`; our tokens carry HA's names, so the mapping is the identity.
A `MutationObserver` on the parent's `<html>` (style/class) follows theme switches, and
`color-scheme` is derived from the background luminance. A cross-origin or sandboxed parent throws;
that is caught and nothing changes: the defaults in `app.css` follow `prefers-color-scheme`.
`?theme=light|dark` (`data-theme` on the root) wins over the bridge.

Status: unit-tested with fake parent windows; **UNVERIFIED against a running Home Assistant** (that
the ingress iframe is same-origin and that these variables are defined on the parent's root).
Verify on the maintainer's HA; the energy colour variable names (`--energy-*`) are still our own
tokens.
